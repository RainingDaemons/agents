## Overview

A plugin that stays inside a single app is just commands in `src-tauri/`. A plugin that will be published is **two packages in one repository**:

- a Rust crate on crates.io, named `tauri-plugin-<name>`;
- an npm package with the JavaScript bindings, normally scoped (`@scope/plugin-<name>` or `@scope/tauri-plugin-<name>`).

Both must be installable, versioned together, and testable from a real Tauri app before they are published. The layout below is the one used by a published plugin (`tauri-plugin-audioplayer`) and is what `npx @tauri-apps/cli plugin new <name>` gives you, plus the files that make publishing repeatable.

*Last verified: 2026-11-18. Re-check the [plugin development guide](https://v2.tauri.app/develop/plugins/) when the CLI template changes.*

## Project Layout

```text
tauri-plugin-<name>/
├── Cargo.toml                  # crate metadata, deps, platform support  -> crates.io
├── build.rs                    # generates permissions + schemas
├── package.json                # npm metadata, exports, publish scripts  -> npm
├── rollup.config.js            # guest-js -> dist-js build
├── tsconfig.json               # type-check only (noEmit)
├── pnpm-lock.yaml              # JS lockfile for reproducible builds
├── src/                        # Rust implementation
│   ├── lib.rs                  # Builder, init(), extension trait
│   ├── commands.rs             # #[tauri::command] wrappers
│   ├── desktop.rs              # #[cfg(desktop)] implementation
│   ├── mobile.rs               # #[cfg(mobile)] implementation
│   ├── error.rs                # serializable error type
│   └── models.rs               # serde types shared with JS
├── guest-js/
│   └── index.ts                # source of the JS bindings
├── dist-js/                    # built bindings, committed here
│   ├── index.js                # ESM
│   ├── index.cjs               # CJS
│   └── index.d.ts              # declarations
├── permissions/
│   ├── default.toml            # what "<name>:default" grants
│   ├── autogenerated/          # generated by build.rs, committed
│   │   ├── reference.md
│   │   └── commands/*.toml
│   └── schemas/schema.json     # generated JSON schema for hand-written permissions
├── android/                    # optional Kotlin library
├── ios/                        # optional Swift package
├── examples/
├── tests/                      # integration tests (cargo test)
├── static/logo.svg             # asset referenced by the README
├── init.js                     # cross-platform bootstrap dispatcher
├── init.ps1 / init.sh          # Windows / POSIX checks and builds
├── README.md                   # install + usage, rendered by both registries
├── LICENSE
├── CONTRIBUTING.md
├── CODE_OF_CONDUCT.md
├── .gitattributes              # binary assets, LF-normalized SVGs
└── .gitignore                  # target/, node_modules/, Cargo.lock, gen/
```

**What ships where:** the crate tarball contains `src/`, `build.rs`, `permissions/`, `Cargo.toml`, `README.md` and `LICENSE` — everything else is excluded in `Cargo.toml`. The npm tarball contains only `dist-js/`, `package.json`, `README.md` and `LICENSE` — controlled by the `files` field. `examples/`, `guest-js/`, `node_modules/` and `target/` never ship.

## Root Crate (`Cargo.toml`)

```toml
[package]
name = "tauri-plugin-<name>"
description = "Tauri <name> Plugin"
version = "0.1.0"
edition = "2024"
rust-version = "1.90"
license = "Apache-2.0"
repository = "https://gitlab.com/<org>/tauri-plugin-<name>"
keywords = ["tauri", "plugin", "<name>"]
categories = ["development-tools"]
authors = [
    "<Name> <email@example.com>"
]

# Keep published tarballs small: examples and JS sources are not needed by consumers.
exclude = [
    "/examples",
    "/dist-js",
    "/guest-js",
    "/node_modules",
]

[dependencies]
tauri = { version = "2" }
serde = "1.0"
thiserror = "2"

[build-dependencies]
tauri-plugin = { version = "2", features = ["build"] }

[dev-dependencies]
serde_json = "1.0"

[package.metadata.platforms.support]
windows = { level = "full" }
linux = { level = "full" }
macos = { level = "full" }
android = { level = "none" }
ios = { level = "none" }
```

Publish-relevant rules:

| Field | Why it matters |
|-------|----------------|
| `name` | Must be `tauri-plugin-<name>` with a lowercase-hyphen identifier; underscores make the build fail. |
| `description` | Required by crates.io; it is the listing text, so write a real sentence. |
| `version` | Single source of truth for the crate; bump it together with `package.json`. |
| `license` | Required by crates.io. Point to the same license as the `LICENSE` file. |
| `repository` | Rendered on crates.io and used by `docs.rs`; broken URLs are not validated, so keep them current. |
| `keywords` / `categories` | Keywords max 5. Categories must exist in the crates.io category list. |
| `exclude` | Without it, `examples/`, `node_modules/` and the JS sources end up in the crate. |
| `links` | Optional. Only set it when the crate really links a native library; it must be unique per native lib. |
| `[build-dependencies] tauri-plugin` | Needed for `build.rs` to generate permissions and scope schemas. |
| `[package.metadata.platforms.support]` | Declares per-platform support (`full` / `partial` / `none` + optional `notes`); it drives the support table on the Tauri plugin pages and tells consumers where the plugin works. |

If the plugin only builds on some targets, add `[package.metadata.docs.rs]` (`targets`, `features`, `default-features = false`); without it `docs.rs` builds for the host and fails on platform-gated dependencies.

A library must **not** commit `Cargo.lock`; ignore it in `.gitignore` so consumers resolve their own graph.

## Rust Source Layout

The split is what lets the same crate expose one API on desktop and mobile:

```rust
// src/lib.rs
use tauri::{
    Manager, Runtime,
    plugin::{Builder, TauriPlugin},
};

#[cfg(desktop)]
mod desktop;
#[cfg(mobile)]
mod mobile;

mod commands;
mod error;
mod models;

pub use error::{Error, Result};
pub use models::*;

#[cfg(desktop)]
use desktop::Example;
#[cfg(mobile)]
use mobile::Example;

/// Extensions to `App`, `AppHandle` and `Window` to access the plugin API.
pub trait ExampleExt<R: Runtime> {
    fn example(&self) -> &Example<R>;
}

impl<R: Runtime, T: Manager<R>> ExampleExt<R> for T {
    fn example(&self) -> &Example<R> {
        self.state::<Example<R>>().inner()
    }
}

pub fn init<R: Runtime>() -> TauriPlugin<R> {
    Builder::new("<name>")
        .invoke_handler(tauri::generate_handler![commands::do_something])
        .setup(|app, api| {
            #[cfg(mobile)]
            let plugin = mobile::init(app, api)?;
            #[cfg(desktop)]
            let plugin = desktop::init(app, api)?;
            app.manage(plugin);
            Ok(())
        })
        .build()
}
```

- `commands.rs` stays thin: `#[command]` functions take `AppHandle`/`State` and delegate to the typed API, so the same logic is callable from Rust.
- `error.rs` exposes `pub type Result<T>` and a `Serialize` impl, because commands must return serializable errors.
- `models.rs` holds the serde structs that also appear in `guest-js/index.ts`; keep field casing in sync (`#[serde(rename_all = "camelCase")]` when the JS side expects camelCase).
- `desktop.rs` / `mobile.rs` each define a struct with the **same name**, so `lib.rs` can alias one to the other with `#[cfg]`.
- `tests/` compiles the crate and exercises pure logic; integration tests must not require hardware, credentials or a GUI.

## Build Script and Permissions

`build.rs` is where the permission surface comes from:

```rust
const COMMANDS: &[&str] = &["list_devices", "play_device", "stop_device"];

fn main() {
    tauri_plugin::Builder::new(COMMANDS)
        .android_path("android") // omit when there is no android/ project
        .ios_path("ios")         // omit when there is no ios/ project
        .build();
}
```

Rules that keep published plugins usable:

- `COMMANDS` must list every registered command in snake_case. A command that exists in `generate_handler!` but not in `COMMANDS` compiles and then fails at runtime with permission denied.
- Output is generated into `permissions/autogenerated/commands/<command>.toml` plus `permissions/autogenerated/reference.md`. Commit them: they document the permission surface and make reviews readable.
- `permissions/default.toml` defines what `"<name>:default"` grants. Only include commands the plugin is useless without.

```toml title="permissions/default.toml"
[default]
description = "Default permissions for the plugin"
permissions = [
  "allow-list-devices",
  "allow-play-device",
  "allow-stop-device",
]
```

- Hand-written permissions and sets live next to `default.toml` (`permissions/<feature>.toml`); scope schemas are generated into `permissions/schemas/schema.json`.
- Treat a command rename as a breaking change: `allow-<old-name>` disappears from the published crate.
- Regenerate (`cargo check` or `cargo build`) before every release so the committed generated files match the code.

## JavaScript Package

```json title="package.json"
{
  "name": "@scope/tauri-plugin-<name>",
  "version": "0.1.0",
  "author": "<Name> <email@example.com>",
  "description": "JS Bindings for Tauri <name> Plugin",
  "repository": {
    "type": "git",
    "url": "git+https://gitlab.com/<org>/tauri-plugin-<name>.git"
  },
  "homepage": "https://gitlab.com/<org>",
  "keywords": ["tauri", "plugin", "<name>"],
  "license": "Apache-2.0",
  "publishConfig": {
    "access": "public"
  },
  "type": "module",
  "types": "./dist-js/index.d.ts",
  "main": "./dist-js/index.cjs",
  "module": "./dist-js/index.js",
  "exports": {
    "types": "./dist-js/index.d.ts",
    "import": "./dist-js/index.js",
    "require": "./dist-js/index.cjs"
  },
  "files": ["dist-js", "README.md"],
  "scripts": {
    "build": "rollup -c",
    "prepublishOnly": "pnpm build",
    "pretest": "pnpm build",
    "prepack": "pnpm build"
  },
  "dependencies": {
    "@tauri-apps/api": "^2.0.0"
  },
  "devDependencies": {
    "@rollup/plugin-typescript": "^12.0.0",
    "rollup": "^4.9.6",
    "typescript": "^5.7.3",
    "tslib": "^2.6.2"
  }
}
```

What each publish-critical piece does:

| Piece | Reason |
|-------|--------|
| `publishConfig.access` | Scoped packages default to private; this makes `npm publish` public without extra flags. |
| `name` | Use the exact name consumers will install. The CLI default is `tauri-plugin-<name>-api`; a scope (`@scope/plugin-<name>`) is recommended and must match the README. |
| `type` + `main`/`module`/`exports` | `type: "module"` plus the `require` condition keeps both ESM and CJS consumers working. |
| `types` | Points into `dist-js`; without a generated `.d.ts` the package ships untyped. |
| `files` | Whitelist. Without it npm publishes `guest-js/`, `src/`, configs and tests. |
| `prepack` / `prepublishOnly` | Rebuild `dist-js` so a stale build never reaches the registry. |
| `dependencies` vs `peerDependencies` | `@tauri-apps/api` as a dependency guarantees a compatible client; as a peer dependency it avoids duplicate copies but requires the app to install it. Pick one and document it. |

`rollup.config.js` reads the paths from `package.json` instead of duplicating them, and must treat `@tauri-apps/api` as external:

```js
import { readFileSync } from 'node:fs'
import { dirname, join } from 'node:path'
import { cwd } from 'node:process'
import typescript from '@rollup/plugin-typescript'

const pkg = JSON.parse(readFileSync(join(cwd(), 'package.json'), 'utf8'))

export default {
  input: 'guest-js/index.ts',
  output: [
    { file: pkg.exports.import, format: 'esm' },
    { file: pkg.exports.require, format: 'cjs' }
  ],
  plugins: [
    typescript({
      declaration: true,
      declarationDir: dirname(pkg.exports.import)
    })
  ],
  external: [
    /^@tauri-apps\/api/,
    ...Object.keys(pkg.dependencies || {}),
    ...Object.keys(pkg.peerDependencies || {})
  ]
}
```

`tsconfig.json` is for type checking only (`rootDir: "guest-js"`, `noEmit: true`, `strict: true`); Rollup emits the files.

`guest-js/index.ts` exports one wrapper per command plus the shared types, always using the namespaced form:

```ts
import { invoke } from '@tauri-apps/api/core'

export interface PlaybackProgress {
  positionSeconds: number
  durationSeconds: number
  isPlaying: boolean
}

export async function playbackProgress(): Promise<PlaybackProgress> {
  return invoke('plugin:<name>|playback_progress')
}
```

`dist-js/` is a build artifact but is committed in this layout so `file:` consumers and the examples work without a build step. Keep it in `exclude` for the crate and in `files` for npm.

## Repository Metadata Files

- **README.md** — the only documentation most consumers read. Include: what the plugin does, `cargo add` + package-manager install lines with the real published names, a usage snippet, supported platforms, and requirements. Relative images (`./static/logo.svg`) render on the git host and in the npm package, but **not** on crates.io; use an absolute URL if the logo must appear there.
- **LICENSE** — must match `license` in both manifests. npm and crates.io require it to be present.
- **CONTRIBUTING.md / CODE_OF_CONDUCT.md** — optional but expected for a public plugin; document the branch flow (feature → `develop` → `release/x.y.z` → `main` → tag) so release tagging is not improvised.
- **static/** — assets referenced by the README, not shipped in either package unless you add them to `files`.
- **.gitattributes** — mark binary assets (`*.png binary`) and normalize text assets to LF (`*.svg text eol=lf`) so packaging diffs stay stable.
- **.gitignore** — at minimum `target/`, `node_modules/`, `Cargo.lock`, and the generated `src-tauri/gen` folders of the examples. Do not ignore `dist-js/` or `permissions/autogenerated/` in this layout.
- **init.js / init.ps1 / init.sh** — developer entry point, not a runtime dependency. `init.js` dispatches to the OS-specific script; both scripts check toolchains, required files, install dependencies frozen, build the JS, then run `cargo fmt --check`, `cargo check`, `cargo test` and the demo build.

## Example App That Consumes the Plugin

An example app is the only way to test the *consumer* experience: capabilities, path dependency, and the npm package.

```toml title="examples/demo/src-tauri/Cargo.toml"
[dependencies]
tauri = { version = "2" }
tauri-plugin-<name> = { path = "../../../" }
```

```json title="examples/demo/package.json"
{
  "dependencies": {
    "@scope/tauri-plugin-<name>": "file:../../"
  }
}
```

```json title="examples/demo/src-tauri/capabilities/default.json"
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "default",
  "description": "enables the default permissions",
  "windows": ["main"],
  "permissions": ["core:default", "<name>:default"]
}
```

```rust title="examples/demo/src-tauri/src/lib.rs"
#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(tauri_plugin_<name>::init())
        .run(tauri::generate_context!())
        .expect("error while running tauri application");
}
```

Points that keep the example honest:

- The `file:` dependency key is the import specifier the frontend uses. Keep it identical to the published package `name`; when the two drift, the demo compiles against a name that no consumer has.
- The demo needs `dist-js/` to exist before `pnpm install`; either commit it or run the plugin's `build` script first.
- Use a distinct app identifier (`com.<org>.tauri-plugin-<name>`) so demo bundles never collide with the real app, and add the plugin's `devUrl`/`frontendDist` so `tauri dev` works from the example.
- Keep at least one desktop example and, for mobile-capable plugins, one that runs the mobile path; `examples/shared/` avoids duplicating UI between them.
- The `gen/schemas/*.json` files referenced by `$schema` are generated by the Tauri build and stay git-ignored.

## Local Bootstrap and Verification

Run the same checks locally that the release depends on:

```bash
# JavaScript bindings
pnpm install --frozen-lockfile
pnpm build                       # guest-js -> dist-js

# Rust
cargo fmt --check
cargo check
cargo test

# Example app (consumes the plugin through path + file: dependencies)
pnpm --dir examples/demo install --frozen-lockfile
pnpm --dir examples/demo build

# Packaging previews
cargo package --list             # crate contents after `exclude`
npm pack --dry-run               # npm tarball contents after `files`
```

The bundled `init.ps1` / `init.sh` wrap exactly this flow and accept `--skip-dependencies` and `--skip-checks`; `init.js` picks the script for the current OS.

## Versioning Both Packages Together

- `Cargo.toml` `version` and `package.json` `version` move in lockstep. A JS package that points at an older crate (or vice versa) is the most common consumer bug report.
- Keep the JS dependency range (`@tauri-apps/api`) compatible with the `tauri` crate major used by the plugin.
- Pre-releases (`0.2.0-alpha.1`) must match on both sides; npm tags and crates.io pre-releases behave differently, so publish the pair together.
- After merging the release branch, tag the merged commit (`vX.Y.Z`) so the crates.io and npm artifacts are traceable to a commit.
- crates.io versions are immutable: yank instead of deleting, and never reuse a version number.

## Pre-Publish Checklist

- [ ] `permissions/autogenerated/` regenerated and committed, `default.toml` reviewed
- [ ] Every new command added in three places: `commands.rs`, `generate_handler!`, `COMMANDS` in `build.rs`
- [ ] `Cargo.toml` and `package.json` versions match
- [ ] `cargo package --list` contains no `examples/`, `node_modules/`, `guest-js/` or `dist-js/`
- [ ] `npm pack --dry-run` contains `dist-js/`, `README.md`, `LICENSE` and nothing else
- [ ] `dist-js/index.js`, `index.cjs` and `index.d.ts` are up to date
- [ ] `README.md` install commands use the names that will actually be published
- [ ] License file present and identical in both manifests
- [ ] Package and crate names are still available on npm / crates.io
- [ ] `cargo publish --dry-run` passes (it runs `build.rs`, so it also validates the permission files)
- [ ] The demo app builds against the plugin and exercises at least one command

## Publish Sequence

1. Bump `version` in `Cargo.toml` and `package.json`, regenerate permissions, commit.
2. Build the bindings (`pnpm build`) and confirm `git status` shows only intended changes.
3. Publish the crate first: `cargo publish`. Rust consumers can install immediately, and the npm README version reference stays valid.
4. Publish the bindings: `npm publish` (or `pnpm publish`); `publishConfig.access: "public"` already handles the scope.
5. Verify from a clean project: `cargo add tauri-plugin-<name>` and add the npm package, then check that `"<name>:default"` appears in a capability file and one command runs.
6. Tag the release (`vX.Y.Z`) and update the changelog.

If step 4 fails after step 3 succeeded, fix and publish a patch of both (a crate version cannot be unpublished). Never publish the JS package before the crate exists: the README would document an install that fails.

## Anti-Patterns

| Anti-pattern | Consequence |
|--------------|-------------|
| No `exclude` in `Cargo.toml` | crate tarball ships examples, JS sources and `node_modules`, and may exceed size limits |
| No `files` in `package.json` | npm publishes `src/`, `guest-js/`, tests and configs |
| Stale `dist-js/` | consumers get bindings that do not match the crate |
| Command added without updating `COMMANDS` | runtime "not allowed" errors for a command that exists |
| `default.toml` granting destructive commands | every consumer inherits the risk by adding `<name>:default` |
| Plural/underscored plugin name | build fails on identifier rules; crate name cannot be published as `tauri-plugin-*` convention |
| Relative logo in README only | the image is broken on crates.io |
| Mismatched crate and npm versions | install succeeds but IPC calls fail or types lie |
| Version published twice / deleted | registries reject it; yank instead |
| Committing `Cargo.lock` for a library | consumers get a pinned graph that hides real resolver problems |
