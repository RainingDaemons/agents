# Tauri v2+ Plugin Authoring

> Build reusable plugins: a Rust crate, optional JavaScript bindings, optional mobile libraries.

This skill is the **producer** side of Tauri plugins. For consuming plugins inside an app (installing official plugins, writing `capabilities/*.json`), use the `tauri-v2` skill. Permission *consumer* rules and generic IPC semantics are in the references below; this file covers what you write *inside* the plugin crate.

A plugin that stays inside one app is just commands in `src-tauri/`. A plugin you intend to reuse or publish is **one repository with two packages plus one permission surface**:

| Artifact | Name | Ships as |
|----------|------|----------|
| Rust crate | `tauri-plugin-<name>` | crates.io |
| JS bindings (optional) | `@scope/plugin-<name>` (CLI default: `tauri-plugin-<name>-api`) | npm |
| Permissions | `<name>:<permission>` identifiers under `permissions/` | inside the crate |
| Mobile libraries (optional) | Kotlin library + Swift package | inside the crate |

**The #1 rule:** a command only works when it exists in three places — the `#[tauri::command]` fn in `commands.rs`, `generate_handler![]` in `lib.rs`, and `COMMANDS` in `build.rs`. Missing the third compiles fine and fails at runtime with permission denied.

## Step 1: Scaffold

```bash
npx @tauri-apps/cli plugin new <name>          # creates ./tauri-plugin-<name>/
npx @tauri-apps/cli plugin new <name> --no-api # Rust crate only, no npm package
npx @tauri-apps/cli plugin new <name> --android --ios
```

Add mobile support to an existing plugin later with `plugin android add` / `plugin ios add` — they bootstrap the native libraries and walk through the required project changes.

Resulting layout:

```text
tauri-plugin-<name>/
├── src/
│   ├── lib.rs          # Builder, init(), extension trait, state
│   ├── commands.rs     # #[tauri::command] wrappers (webview-facing)
│   ├── desktop.rs      # #[cfg(desktop)] implementation
│   ├── mobile.rs       # #[cfg(mobile)] implementation
│   ├── error.rs        # serializable error type
│   └── models.rs       # serde structs shared with JS
├── permissions/        # permission files + generated allow/deny per command
├── guest-js/index.ts   # JS binding sources
├── dist-js/            # built bindings (esm + cjs + .d.ts)
├── android/            # optional Kotlin library
├── ios/                # optional Swift package
├── build.rs            # generates permissions and scope schemas
├── Cargo.toml
└── package.json
```

## Step 2: Name and identifier rules

The `{plugin-name}` is used for the crate name, the `tauri.conf.json > plugins` key, the permission prefix, and the `plugin:<name>|command` IPC prefix — keep all four identical. It must satisfy Tauri's identifier syntax:

- lowercase ASCII letters, digits, hyphens
- no leading or trailing hyphen, no underscores, no uppercase
- a single `:` only when prefixed (`<name>:allow-read`)
- base name ≤ 64 chars; prefixed identifier ≤ 129 chars

| Identifier | Valid? |
| --- | --- |
| `sqlite-store` | ✓ |
| `sqlite-store:allow-read` | ✓ |
| `sqlite_store` | ✗ (underscore) |
| `SqliteStore` | ✗ (uppercase) |
| `-sqlite` | ✗ (leading hyphen) |
| `sqlite::store` | ✗ (multiple separators) |

Violations fail the build with `identifiers can only include lowercase ASCII, hyphens which are not leading or trailing, and a single colon if using a prefix`. The offending value is normally the crate name in `Cargo.toml` or an identifier in a `permissions/*.toml`.

## Step 3: Cargo.toml

```toml
[package]
name = "tauri-plugin-<name>"
description = "Tauri <name> Plugin"
version = "0.1.0"
edition = "2024"
rust-version = "1.90"
license = "Apache-2.0"
repository = "https://example.com/<org>/tauri-plugin-<name>"
keywords = ["tauri", "plugin", "<name>"]
categories = ["development-tools"]

# Keep the published tarball small; only src/, build.rs, permissions/, README, LICENSE should ship.
exclude = ["/examples", "/dist-js", "/guest-js", "/node_modules"]

[dependencies]
tauri = { version = "2" }
serde = { version = "1", features = ["derive"] }
thiserror = "2"

[build-dependencies]
tauri-plugin = { version = "2", features = ["build"] }

[package.metadata.platforms.support]
windows = { level = "full" }
linux = { level = "full" }
macos = { level = "full" }
android = { level = "partial", notes = "Access is restricted to the Application folder by default" }
ios = { level = "none" }
```

- `[build-dependencies] tauri-plugin` with `features = ["build"]` is what makes `build.rs` generate permissions and scope schemas.
- `[package.metadata.platforms.support]` drives the platform support table on `v2.tauri.app/plugin/`; use `full` / `partial` (+`notes`) / `none` and keep it honest.
- Platform-gated code needs `[package.metadata.docs.rs]` (`targets`, `features`, `default-features = false`) so docs.rs does not build for the host and fail.
- A library must **not** commit `Cargo.lock`; ignore it so consumers resolve their own graph.
- `license` must match the `LICENSE` file; crates.io and npm both require it.

## Step 4: Rust structure

`desktop.rs` and `mobile.rs` each define a struct with the **same name**, so `lib.rs` can alias one to the other with `#[cfg]` and expose a single API through an extension trait:

```rust
// src/lib.rs
use tauri::{
    Manager, Runtime,
    plugin::{Builder, TauriPlugin},
};

#[cfg(desktop)]
mod desktop;
#[cfg(mobile)]
mod mobile;

mod commands;
mod error;
mod models;

pub use error::{Error, Result};

#[cfg(desktop)]
use desktop::Example;
#[cfg(mobile)]
use mobile::Example;

/// Extensions to `App`, `AppHandle` and `Window` to reach the plugin API.
pub trait ExampleExt<R: Runtime> {
    fn example(&self) -> &Example<R>;
}

impl<R: Runtime, T: Manager<R>> ExampleExt<R> for T {
    fn example(&self) -> &Example<R> {
        self.state::<Example<R>>().inner()
    }
}

pub fn init<R: Runtime>() -> TauriPlugin<R> {
    Builder::new("<name>")
        .invoke_handler(tauri::generate_handler![commands::do_something])
        .setup(|app, api| {
            #[cfg(mobile)]
            let plugin = mobile::init(app, api)?;
            #[cfg(desktop)]
            let plugin = desktop::init(app, api)?;
            app.manage(plugin);
            Ok(())
        })
        .build()
}
```

Responsibilities:

- `lib.rs` — builder wiring, shared logic callable from both platforms, state via `app.manage(...)`.
- `commands.rs` — thin `#[command]` wrappers that take `AppHandle`/`State` and delegate to the typed API, so the same logic is callable from Rust (`app.example().do_something()`).
- `desktop.rs` / `mobile.rs` — the actual implementation per platform.
- `error.rs` — `pub type Result<T>` plus a `Serialize` impl; command errors must serialize.
- `models.rs` — serde structs that also appear in `guest-js/index.ts`; keep casing in sync (`#[serde(rename_all = "camelCase")]` when JS expects camelCase).

State works exactly like in an app: `app.manage(Mutex::new(Store::default()))` in `setup`, then `State<'_, Mutex<Store>>` in commands.

## Step 5: Commands

```rust
// src/commands.rs
use tauri::{command, ipc::Channel, AppHandle, Runtime, Window};

#[command]
async fn upload<R: Runtime>(
    app: AppHandle<R>,
    window: Window<R>,
    on_progress: Channel,
    url: String,
) {
    // delegate to crate::Example::upload(...)
    on_progress.send(100).unwrap();
}
```

Register it on the plugin builder (not the app builder):

```rust
Builder::new("<name>")
    .invoke_handler(tauri::generate_handler![commands::upload])
```

Then bind it in `guest-js/index.ts` with the namespaced prefix, and build the bindings before testing:

```ts
import { invoke, Channel } from '@tauri-apps/api/core'

export async function upload(
  url: string,
  onProgressHandler: (progress: number) => void
): Promise<void> {
  const onProgress = new Channel<number>()
  onProgress.onmessage = onProgressHandler
  await invoke('plugin:<name>|upload', { url, onProgress })
}
```

- Command name in `invoke` is the snake_case fn name with the `plugin:<name>|` prefix.
- Keep the wrapper free of business logic — it only binds arguments and types.
- Async commands cannot borrow across await points: take owned types (`String`, not `&str`).
- Scoped commands take `tauri::ipc::CommandScope<'_, Entry>` (per-command scope) or `GlobalScope<'_, Entry>`; check both `allows()` and `denies()`.

## Step 6: Permissions surface

Everything under `permissions/` is authored by you and granted by the consuming app. By default every command is denied — a plugin without a `default.toml` is unusable.

**Autogenerated command permissions** (`build.rs`):

```rust
const COMMANDS: &[&str] = &["list_devices", "play_device", "stop_device"];

fn main() {
    tauri_plugin::Builder::new(COMMANDS)
        .android_path("android") // omit when there is no android/ project
        .ios_path("ios")         // omit when there is no ios/ project
        .build();
}
```

- `COMMANDS` must list every command in snake_case. Extra entries are harmless; missing ones give runtime "not allowed" errors.
- Output lands in `permissions/autogenerated/commands/<command>.toml` plus `permissions/autogenerated/reference.md`. Commit both.
- Regenerate (`cargo check` / `cargo build`) before every release.

**Default set** — what `"<name>:default"` expands to. Include only commands the plugin is useless without; destructive ones stay opt-in:

```toml title="permissions/default.toml"
[default]
description = "Default permissions for the plugin"
permissions = ["allow-list-devices", "allow-play-device"]
```

**Permission sets** group one API surface into a single grantable identifier:

```toml title="permissions/playback.toml"
[[set]]
identifier = "allow-playback"
description = "Allows starting and stopping playback"
permissions = ["allow-play-device", "allow-stop-device"]
```

**Hand-written permissions** allow/deny specific commands:

```toml title="permissions/start-server.toml"
[[permission]]
identifier = "allow-start-server"
description = "Enables the start_server command."
commands.allow = ["start_server"]
```

**Scopes** are Rust structs deriving `schemars::JsonSchema`; the schema is registered in `build.rs` so consumers get autocomplete and validation in their `allow`/`deny` blocks. `schemars` goes in **both** `[dependencies]` and `[build-dependencies]` because `scope.rs` is shared with the build script:

```rust
#[path = "src/scope.rs"]
mod scope;

fn main() {
    tauri_plugin::Builder::new(COMMANDS)
        .global_scope_schema(schemars::schema_for!(scope::Entry))
        .build();
}
```

Renaming or removing a command is a **breaking change**: `allow-<old-name>` disappears from the published crate. See [`references/capabilities-reference.md`](references/capabilities-reference.md#plugin-permission-authoring) for the full authoring rules.

## Step 7: Lifecycle hooks

| Hook | When | Typical use |
|------|------|-------------|
| `setup` | plugin is initialized | `app.manage(state)`, register mobile plugins, spawn background tasks |
| `on_navigation` | webview attempts a navigation | validate/track URLs; return `false` to cancel |
| `on_webview_ready` | a new window is created | inject per-window listeners/init scripts |
| `on_event` | event loop events (`RunEvent`) | `ExitRequested` / `Exit` cleanup, e.g. flush state to disk |
| `on_drop` | plugin is deconstructed | release resources |

```rust
Builder::new("<name>")
    .setup(|app, _api| {
        app.manage(DummyStore(Default::default()));
        Ok(())
    })
    .on_event(|app, event| {
        if let tauri::RunEvent::Exit = event {
            // flush app.path().app_local_data_dir()/store.json
        }
    })
    .on_navigation(|_window, url| url.scheme() != "forbidden")
```

Background loops belong in `setup` with a cloned `AppHandle`; never block the main thread inside a hook.

## Step 8: Plugin configuration

Plugin config lives under `tauri.conf.json > plugins > <name>` in the consuming app and is parsed at runtime by the `Builder`:

```rust
#[derive(serde::Deserialize)]
pub struct Config {
    timeout: usize,
}

pub fn init<R: Runtime>() -> TauriPlugin<R, Config> {
    Builder::<R, Config>::new("<name>")
        .setup(|_app, api| {
            let _timeout = api.config().timeout;
            Ok(())
        })
        .build()
}
```

Use `Builder::<R, Option<Config>>` when config is optional. On mobile, read the same values natively (`getConfig(Config::class.java)` on Android, `parseConfig(Config.self)` on iOS in `load`).

## Step 9: JavaScript bindings package

Only relevant when scaffolded with an API (`--no-api` skips it).

```ts title="guest-js/index.ts"
import { invoke } from '@tauri-apps/api/core'

export interface PlaybackProgress {
  positionSeconds: number
  durationSeconds: number
  isPlaying: boolean
}

export function playbackProgress(): Promise<PlaybackProgress> {
  return invoke('plugin:<name>|playback_progress')
}
```

Plugin events from native code reach JS through `addPluginListener`, which is gated by the same capability as commands:

```ts
import { addPluginListener, type PluginListener } from '@tauri-apps/api/core'

export function onPlayback(handler: (p: PlaybackProgress) => void): Promise<PluginListener> {
  return addPluginListener('<name>', 'playback', handler)
}
```

Publish-critical `package.json` fields:

```json
{
  "name": "@scope/plugin-<name>",
  "version": "0.1.0",
  "type": "module",
  "types": "./dist-js/index.d.ts",
  "main": "./dist-js/index.cjs",
  "module": "./dist-js/index.js",
  "exports": {
    "types": "./dist-js/index.d.ts",
    "import": "./dist-js/index.js",
    "require": "./dist-js/index.cjs"
  },
  "files": ["dist-js", "README.md"],
  "publishConfig": { "access": "public" },
  "scripts": {
    "build": "rollup -c",
    "prepack": "pnpm build",
    "prepublishOnly": "pnpm build"
  },
  "dependencies": { "@tauri-apps/api": "^2.0.0" }
}
```

- `files` is a whitelist — without it npm publishes `guest-js/`, `src/`, configs and tests.
- `publishConfig.access` is required for scoped packages, which default to private.
- `prepack` / `prepublishOnly` stop a stale `dist-js/` from reaching the registry; rebuild before release.
- Rollup emits ESM + CJS + declarations and must treat `@tauri-apps/api` (and the dependency maps) as `external`.
- `tsconfig.json` is type-check only (`rootDir: "guest-js"`, `noEmit: true`, `strict: true`).
- `dist-js/` is a build artifact but is committed in this layout so `file:` consumers and examples work without a build step. Keep it in the crate `exclude` and in the npm `files`.

## Step 10: Mobile (Kotlin / Swift)

- Native commands are Kotlin classes annotated `@TauriPlugin` extending `app.tauri.plugin.Plugin`, or Swift classes extending `Tauri.Plugin`. Methods annotated `@Command` (Kotlin) / `@objc ... (_ invoke: Invoke)` (Swift) are callable from Rust and JS.
- Rust calls them through `PluginHandle::run_mobile_plugin`:

```rust
impl<R: Runtime> Example<R> {
    pub fn open_camera(&self, payload: CameraRequest) -> crate::Result<Photo> {
        self.0.run_mobile_plugin("openCamera", payload).map_err(Into::into)
    }
}
```

- Arguments: Kotlin classes annotated `@InvokeArg` (`lateinit var x: T` required, `var x: T? = null` optional, `var x: T = default` defaulted); Swift `Decodable` classes in `parseArgs`. **Swift has no default values** — use an optional and apply the default in the command.
- Android native commands run on the main thread: long work must go through a coroutine scope (`Dispatchers.IO`) or the UI freezes / ANRs.
- Runtime permissions: declare them in the `@TauriPlugin(permissions = [...])` annotation (Android) or override `checkPermissions` / `requestPermissions` (iOS). Tauri auto-exposes `checkPermissions` and `requestPermissions` commands; call them as `plugin:<name>|checkPermissions`.
- Native events: `trigger("event", payload)` on both platforms, consumed via `addPluginListener`.
- Calling Rust from mobile: JNI on Android (`jni` crate under `[target.'cfg(target_os = "android")'.dependencies]`, `Java_<package>_<class>_<method>` exports) and C FFI on iOS (`@_silgen_name` on the Swift side, `#[no_mangle] extern "C"` on the Rust side, with a matching free function for returned C strings).
- Android 16KB page support: build with NDK 28+, or add `rustflags = ["-C", "link-arg=-Wl,-z,max-page-size=16384"]` for `aarch64-linux-android` in `.cargo/config.toml`.

Full native samples: [`references/mobile-plugins-development.md`](references/mobile-plugins-development.md).

## Step 11: Verify from a consuming app

The example app is the only way to test the *consumer* experience (path dependency, `file:` npm link, capabilities):

```toml title="examples/demo/src-tauri/Cargo.toml"
[dependencies]
tauri-plugin-<name> = { path = "../../../" }
```

```json title="examples/demo/src-tauri/capabilities/default.json"
{
  "$schema": "../gen/schemas/desktop-schema.json",
  "identifier": "default",
  "windows": ["main"],
  "permissions": ["core:default", "<name>:default"]
}
```

```rust title="examples/demo/src-tauri/src/lib.rs"
tauri::Builder::default()
    .plugin(tauri_plugin_<name>::init())
    .run(tauri::generate_context!())
    .expect("error while running tauri application");
```

- Use a distinct identifier (`com.<org>.tauri-plugin-<name>`) so demo bundles never collide with real apps.
- Keep the npm `file:` key identical to the published package `name`, and make sure `dist-js/` exists before installing.

Verification commands:

```bash
pnpm install --frozen-lockfile && pnpm build   # guest-js -> dist-js
cargo fmt --check && cargo check && cargo test # also regenerates permissions
cargo package --list                           # crate contents after `exclude`
npm pack --dry-run                             # npm tarball contents after `files`
```

## Known Issues Prevention

| Issue | Root cause | Solution |
|-------|-----------|----------|
| Frontend gets "not allowed" for an existing command | Command missing from `COMMANDS` in `build.rs` | Add it and rebuild to regenerate permissions |
| `plugin:<name>|<cmd>` not found | Command missing from `generate_handler!` | Add to the plugin builder's handler |
| `app.example()` panics | Plugin struct not managed in `setup` | `app.manage(plugin)` in `Builder::setup` |
| Build fails on identifier syntax | Underscore/uppercase/trailing hyphen in plugin or permission identifier | Rename to lowercase-hyphen form |
| Plugin works on desktop, breaks on mobile | Desktop-only API used unconditionally | Split into `desktop.rs` / `mobile.rs`, gate with `#[cfg]` |
| `run_mobile_plugin` errors on Android | Command name mismatch or long work on the main thread | Match the annotated name; move work to a coroutine |
| Scope args never arrive | `schemars` only in `[dependencies]` | Add it to `[build-dependencies]` and register the schema |
| Published JS incompatible with the crate | `dist-js/` stale or versions out of sync | Bump both manifests together, rebuild before publish |
| Crate tarball huge | No `exclude` | Exclude `examples/`, `dist-js/`, `guest-js/`, `node_modules/` |
| npm package leaks sources | No `files` whitelist | Ship only `dist-js`, `README.md`, `LICENSE` |

## Release Checklist

- [ ] Every command present in `commands.rs`, `generate_handler![]` and `COMMANDS`
- [ ] `permissions/autogenerated/` regenerated and committed; `default.toml` reviewed
- [ ] `Cargo.toml` and `package.json` versions match; `@tauri-apps/api` range compatible with the `tauri` major
- [ ] `cargo package --list` and `npm pack --dry-run` contain only intended files
- [ ] `dist-js/index.js`, `index.cjs`, `index.d.ts` up to date
- [ ] README install lines use the names that will actually be published (absolute logo URL for crates.io)
- [ ] `cargo publish --dry-run` passes (it runs `build.rs`, validating permission files)
- [ ] Demo app builds against the plugin and exercises at least one command
- [ ] Publish order: crate first, then npm; tag the merged commit `vX.Y.Z`
